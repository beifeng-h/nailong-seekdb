## 1. 问题理解与学习规划

### 1.1 先把题目读成需求，而不是读成功能列表

赛题不是"写一个向量数据库"，而是**在受限环境里复现判题器的行为**。
读题时最先确认的三件事：

| 要确认的事 | 出处 | 得到的结论 |
| --- | --- | --- |
| 公开用例有多少、正式用例有多少 | `mysqltest/README.md` | 公开 20 组 / 95 条 SQL；**正式 29 个用例**，组织方另保留 9 个用例的具体输入与操作序列 |
| "通过公开用例"意味着什么 | 同上 | 「公开样例通过不代表完整功能准入通过」；「**隐藏的是测试数据，而非功能要求**」 |
| 进程怎么和判题器说话 | `STDIO_PROTOCOL.md` | JSONL，一行一报文，主动 ready，响应回传 `id`，`ok` 必须是布尔值 |

这三条直接决定了后面所有工作的形状：公开用例是**回归基线**而不是
**验收标准**；功能要求要按题包正文列的清单逐条实现；通信要按协议文档
逐字对齐。

### 1.2 规划：从协议到语义，从语义到资源

据此把开发拆成有明确验证手段的阶段（后续提交顺序与阶段基本对应）：

```text
阶段 A  容器与构建链路      验证手段：镜像能构建、默认入口正确
阶段 B  文件 IO 与持久化    验证手段：位置化读、短读、偏移越界、中断读
阶段 C  事务与原子性        验证手段：强杀恢复、失败语句不部分生效
阶段 D  向量索引            验证手段：增删改后索引一致、重启后一致
阶段 E  数值序列化          验证手段：浮点字节级回归、BIGINT 边界
阶段 F  正式 JSONL 协议     验证手段：组织方原版 protocol_check/run.py
```

阶段 F 放在最后不是偶然：前面所有阶段都在自研协议上验证，而判题器用
的是 JSONL。协议不最后一轮对齐，前面所有"通过"都可能只是"符合我自己的
协议"。

### 1.3 需求清单先于代码

动手前先把题包「正式验收要求仍然公开」抄成可勾选清单
（见 `AGENT_PROMPT.md` §1 的清单模板）。抄的过程中就暴露出两类容易
漏掉的要求：

- **题包正文里有、公开用例里没有**的：拒绝 NaN/Infinity/维度错误/
  float32 溢出；失败语句不部分生效；崩溃后已提交数据保留；超过内存
  限额的数据；ANN 的过滤、有效 ID、无重复、召回率。
- **藏在断言格式里的**：`.result` 里的 `{}` 不是"输出 `{}`"，
  而是"这条语句必须成功且没有额外字段断言"——但协议层仍然必须回传
  `id` 和 `ok:true`。浮点比较容差是 `1e-5`，`unordered` 用多重集合
  比较且重复行不能丢。

## 2. Prompt 设计与迭代

Agent Prompt 的演进不是"越写越长"，而是**每一条新规则都对应一次真实的
失败或判断失误**。完整的结构化记录见
[`prompt_iteration.json`](prompt_iteration.json)，下表是摘要。

| 版本 | 引入的关键规则 | 触发它的事实 | 证据 |
| --- | --- | --- | --- |
| v1 | 先读题包、抄需求清单；不预存答案 | 题包明文禁止预存样例答案 | `mysqltest/README.md` |
| v2 | 失败语句整条不生效 | 本地差分跑出多行 INSERT 部分生效 | `verification/python_public_check.first_run.txt` |
| v3 | 公开用例通过 ≠ 正式准入；错误码要语义名 | 正式 29 例 vs 公开 20 例 | `mysqltest/README.md` |
| v4 | 协议硬约束（ready 时序、逐条 flush、`id` 原样回传、`ok` 布尔、shutdown 后不再输出） | 自研 development protocol 与正式 JSONL 协议不一致 | `63055c809`、`5247fd706`、`e4c8c178c` |
| v5 | 数值序列化字节级一致（float32、17 位有效数字、有符号零、次正规数、BIGINT 边界） | 浮点输出格式与判题器不一致 | `a33ea6e05`、CI `42618083030` |
| v6 | 位置化文件读；短读/大偏移/中断读要单独验 | 偏移越界与短读风险 | `b222024f7`、`d033d2fd2`、CI `42600565765` |
| v7 | 索引维护不得破坏事务语义；索引原子发布 | 索引与事务交互是独立失效面 | `e5b5c83e1`、CI `42611519248` |

### 2.1 最有价值的一次迭代：v2（原子性）

这条规则不是从题包抄来的，是被**独立实现差分跑出来的**。

用组织方**未修改**的 `protocol_check/run.py` + `_assertions.py` + 题包
驱动另一套独立实现时，`transaction_failed_insert` 一例报出：

```text
rows: [[1], [2], [3], [4]] != [[1], [2], [3]]
```

失败的多行 INSERT 把**前一行留在了表里**。根因是逐行写入时后一行校验
失败，前一行的改动没有撤销。这正是题包「失败语句不能部分生效」
要求禁止的行为。

**Prompt 里的对应改动**：把"失败语句整条不生效"从"注意事项"提升为
**红线**，并要求按三种情况分别验证——自动提交、显式事务中、崩溃之后。

### 2.2 最有价值的一次收敛：v4（协议）

在 v4 之前，开发自研了一套 development stdio 协议
（`01689695d`），它能跑通自测，但在正式协议面前是错的：握手对象不
匹配、请求是 SQL 文本而不是 JSON、响应字段名不同。

改动不是"再改改协议"，而是**把判题器当作唯一的规格来源**：协议文档
逐条抄进 Prompt，逐条变成可执行的检查项。落地结果是三个提交
（`63055c809` → `5247fd706` → `e4c8c178c`），CI
`42819609767`（提测分支，`e4c8c178c`）用**组织方原版**
`protocol_check/run.py` 跑完握手与全部公开用例，结论 `success`。

## 3. 验证纠错与独立判断

### 3.1 独立判断的锚点：先过滤还是先 TopK

这是整个赛题里最容易做错、也最容易被"看起来对"掩盖的一处语义。
题目问：WHERE 只允许 A 类记录，但全表最近的一条属于 B 类，应该
"先全表取 Top1 再过滤"还是"先过滤出 A 类再取 Top1"？

本人给出的判断（原话见 `conversation.json` 的 `u4`）：

> 先过滤出 A 类再取 Top1，先 top1 可能拿到空结果，也就是 B 类，
> 优先过滤出符合条件的结果才对

Agent 随后用编译好的测试程序做了独立实验（`conversation.json` 的
`filter-order` 条目，记录了数据集、执行方式与真实输出）：全表 Top1 是
`id=1/other`，过滤后剩 0 条；先过滤得到 `id=2`，欧氏距离 10。

**这个判断的独立性在于**：它不是从"实现返回什么"读出来的，而是先
在语义层面论证，再用实验验证；而且实现侧的写法必须服从这个判断，
不是反过来。

### 3.2 验证手段一：组织方原版驱动，不自研替代品

最有价值的验证环境是**组织方自己的工具**：

- `protocol_check/run.py`——按正式顺序等待 ready、发请求、读响应，
  支持用例内重启与模式切换，第一个超时后停止并标记 SKIPPED；
- `protocol_check/_assertions.py`——判题语义的复刻（浮点容差、
  多重集合比较、错误码断言）；
- `protocol_check/config.json`——判题资源与比较参数（启动 120 秒、
  单请求 60 秒、普通用例 600 秒、2 CPU / 2 GiB / 128 PID、容差 1e-5）。

CI `42819609767` 用的就是这一套，未做任何修改：

```text
python3 protocol_check/run.py --image minivectordb-m11 --handshake-only ...
python3 protocol_check/run.py --image minivectordb-m11 ...
```

**携带本材料的那次提测**（CI `42941464341`，`head_sha=e158a338f`，结论
`success`）的实际输出是：

```text
{"scope": "native-stdio-public-and-edge-checks", "passed": true}
{"scope": "public-protocol-check", "passed": true}   <- handshake
{"scope": "public-protocol-check", "passed": true}   <- 20 组公开用例，20/20 PASS
```

逐用例状态原样存于
[`verification/submission_ci_public_check.json`](verification/submission_ci_public_check.json)
（从该次运行的日志里还原），其中 `vector_index_maintenance` 与
`transaction_failed_insert` 均为 `PASS`。

### 3.3 验证手段二：独立真值，不用自己的输出自证

对照实现的查询结果不能自己给自己作证。可核验的独立真值来源有三类：

1. **题包断言**（`mysqltest/cases/*.result`）——组织方给出的期望；
2. **独立参考实现**——例如用 NumPy 按周期键算出的精确距离真值，
   与实现返回的 id、行序、距离逐条比对（`conversation.json` 的
   `m6-query-development-baseline`：10000 行 / 128 维 / 1000 次查询
   全部与独立真值一致）；
3. **另一套独立实现**——见 3.4。

### 3.4 验证手段三：跨实现差分（本次最有价值的一次纠错）

除了把提测实现本身验透，还用**同一份官方题包**去驱动另一套独立实现
（本机的 Python 参考实现），做差分。两套实现语言不同、代码不同，
被同一份组织方断言审判——差异立刻暴露出来。

**首轮结果：14 / 20 通过。** 6 个失败项与根因：

| 失败用例 | 根因 | 性质 |
| --- | --- | --- |
| `vector_euclidean`、`storage_mutations`、`vector_ties_and_filter`、`vector_float32` | 不认识题包方言里的 `L2_DISTANCE`（只有 `DISTANCE` / `VECTOR_DISTANCE`） | 方言缺口 |
| `transaction_failed_insert` | 多行 INSERT 中后一行失败时，前一行留在了表里 | **真实原子性缺陷** |
| `vector_index_maintenance` | 没有 `CREATE VECTOR INDEX` | 功能缺口（本地实现明确不做 ANN 索引） |

三个值得记录的判断：

1. **通过的用例也可能"通过了错的原因"。** `sql_unsupported` 要求
   `ALTER TABLE` 必须报错，本地实现确实报了错——但原因是执行器**根本
   没有 ALTER 分支**（解析器能解析，派发时忘了接），而它自己的
   SPEC-006 却写着"必须支持 ALTER TABLE"。也就是说：这条用例是绿的，
   同时规格与实现是脱节的。只看断言结果会漏掉这一点。
2. **"验证失效"本身也要验证。** 仓库里 `test_topk_works_without_numpy`
   用的是 `find_module` 导入钩子来屏蔽 numpy，而该钩子 **Python 3.12
   起已被移除**——于是 numpy 根本没被挡住，"无 numpy 纯 Python 回退路径"
   这条验收在 3.12 上等于没测。已改为同时实现 `find_spec`。
   换句话说：**一条绿色的测试，也可能已经很久没有在验证它声称的东西。**
3. **修完要重跑全量，不能只看修的那条。** 修复后本地达到 **19 / 20**，
   仓库自身 109 个用例全绿，`sddctx doctor` 退出码 0；唯一未通过的是
   `vector_index_maintenance`（本地实现不做 ANN 索引，已在 SPEC-006
   登记为不在契约范围内），提测实现侧由 CI `42611519248` 与
   `42819609767` 覆盖。

   同一份题包下两套实现对同一用例给出不同结论，本身就是最有说服力的
   证据：本地参考实现在 `vector_index_maintenance` 上失败，提测实现在
   同一用例上 PASS——说明断言确实在区分实现，而不是两边都"看起来对"。

原始报告见 [`verification/python_public_check.result.json`](verification/python_public_check.result.json)
（组织方 `result.json` 原样拷贝）与
[`verification/python_public_check.cases.json`](verification/python_public_check.cases.json)。

### 3.5 验证纪律里最要紧的一句

题包自测工具的 `result.json` 里 `passed=true`，只表示**本次选中的
检查**通过。题包原文：握手通过不代表 SQL 正确；公开用例通过不代表
正式 29 个用例或性能/Agent 评审通过。本材料不把"公开用例通过"写成
"评测通过"。

## 4. 总结复盘与知识迁移

### 4.1 复盘：这个题真正在考什么

做完之后回头看，这道题考的不是"能不能写一个向量数据库"，而是三件事：

1. **能不能把规格读成清单。** 公开用例只覆盖 20 组，正式验收有 29 个
   且隐藏了 9 个用例的输入。"隐藏的是测试数据，而不是功能要求"——
   这句话把"照着公开用例写"和"按要求实现"区分成了两种做法。
2. **能不能把外部系统当成唯一规格来源。** 协议以判题器实际行为为准，
   语义以题包正文为准，自研的"差不多的协议"全部作废。
3. **能不能给自己的结论找到独立证据。** 用自己的输出自证，用
   "看起来对"的语义自证，用"全绿"自证——都过不了正式评审。

### 4.2 知识迁移：把一次性结论沉淀成可执行的东西

这次工作中真正被"迁移"出去的不是聊天记录，而是三样**可复跑的资产**：

1. **规格**。赛题语义被固化成 `SPEC-006` 的可勾选需求
   （本次新增 `REQ-MVDB-9` 赛题 JSONL 协议、`REQ-MVDB-10` 语句级原子性，
   并修正 `REQ-MVDB-1` 关于 `ALTER TABLE` 的口径），
   每条需求都带 `verified_by` 指向具体用例。
2. **回归用例**。新增协议端到端、原子性、`L2_DISTANCE`
   别名、`ALTER TABLE` 拒绝等用例，共 109 个，覆盖从协议握手到崩溃恢复
   的完整链路。
3. **跨语言的两套实现 + 同一份外部断言**。C++ 提测实现（容器、CI 验证）
   与 Python 参考实现（本机、官方驱动差分）互为参照；任何一侧的行为
   漂移都会被对方的断言抓到。这比"只有一套实现 + 自己写的测试"更难
   自欺。

### 4.3 迁移到下一个任务的方法

这三条可以直接带走：

- **先找外部规格源**（官方题包、协议文档、判题器行为），
  把它们逐条抄成清单，再动手；
- **给"通过"配一个独立判据**，并且明确写下这个判据**不覆盖**什么；
- **让结论带上出处**（提交号 / CI 运行号 / 文件路径 / 真实输出），
  没有出处的话就不写进结论。
